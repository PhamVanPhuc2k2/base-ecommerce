# P2.2 — Phân quyền (RBAC): Thiết kế

> Thuộc P2, xem [tổng quan](2026-09-30-p2-tong-quan.md). Chủ dự án chốt:
> **quyền cố định trong code, vai trò + gán vai trò trong DB.**

## 1. Phạm vi

**Có:** danh sách quyền trong code; bảng `roles`, `role_permissions`,
`user_roles`; middleware `RequirePermission`; API quản trị vai trò và gán vai
trò; `GET /me` trả kèm quyền; lệnh `admintool` cấp vai trò cho người đầu tiên;
**gỡ hẳn `X-Admin-Key`** (P0.2 → P2.1).

**Không:** giao diện quản trị; quyền theo từng bản ghi ("chỉ sửa sản phẩm của
kho mình"); nhật ký thao tác quản trị (audit log).

## 2. Quyết định

### 2.1. Quyền là hằng số trong code

| Quyền | Cho phép |
|---|---|
| `catalog.products.write` | tạo, sửa, đăng bán sản phẩm; thêm/sửa phiên bản |
| `catalog.taxonomy.write` | danh mục, thương hiệu, định nghĩa thuộc tính, gán thuộc tính cho danh mục |
| `media.upload` | cấp URL upload, xác nhận ảnh |
| `iam.roles.manage` | xem quyền, tạo/sửa/xóa vai trò, gán vai trò cho người dùng |

Thêm quyền = thêm tính năng = sửa code. Vai trò trong DB chỉ được chứa quyền có
trong danh sách này — domain kiểm, không phải DB (danh sách sống trong code).

### 2.2. Vai trò `super_admin` là vai trò HỆ THỐNG

Migration tạo sẵn `super_admin` với cờ `is_system`: có MỌI quyền **kể cả quyền
thêm sau này** (không liệt kê từng quyền — liệt kê thì quyền mới thêm ở P3 không
tự có), và không sửa/xóa được qua API.

### 2.3. Người đầu tiên: lệnh `admintool`, không phải API

`go run ./cmd/admintool grant-role <email> super_admin` — chạy trên máy có quyền
vào database. Không có endpoint "tạo admin đầu tiên": endpoint như vậy là lỗ
hổng chờ ai đó gọi trước chủ nhà.

### 2.4. Quyền tra MỖI request, cache 5 phút, xóa cache khi đổi

Access token không mang quyền (P2.1 mục 2.3). `RequirePermission` tra tập quyền
của người dùng qua Redis `iam:perms:<user>` (TTL 5 phút); đổi gán vai trò → xóa
khóa của người đó; đổi quyền của một vai trò → xóa khóa của MỌI người đang giữ
vai trò đó. Gỡ quyền có hiệu lực ngay, không chờ token hết hạn. Tài khoản bị
khóa → tập quyền rỗng.

### 2.5. Không tự đổi vai trò của chính mình

`PUT /admin/users/{mình}/roles` → 422 `CANNOT_CHANGE_OWN_ROLES`. Không có quy
tắc này thì super admin duy nhất tự gỡ vai trò của mình là không còn ai quản trị
được — và chỉ `admintool` cứu được.

### 2.6. 401 vs 403

Thiếu/hỏng token → 401 `UNAUTHENTICATED`. Token tốt nhưng thiếu quyền → 403
`FORBIDDEN`. Đổi thứ tự (403 trước khi biết là ai) là nói cho người lạ biết
endpoint nào tồn tại và cần quyền gì.

## 3. API

| Method | Đường dẫn | Quyền |
|---|---|---|
| GET | `/admin/permissions` | `iam.roles.manage` |
| GET/POST | `/admin/roles` | `iam.roles.manage` |
| PATCH/DELETE | `/admin/roles/{id}` | `iam.roles.manage` — xóa vai trò còn người giữ → 409 `ROLE_IN_USE` |
| PUT | `/admin/users/{id}/roles` | `iam.roles.manage` |
| GET | `/me` | đăng nhập — thêm `permissions: string[]` |

Mọi `/admin/*` cũ: `X-Admin-Key` → Bearer + quyền theo bảng 2.1.

## 4. Kiểm chứng

| # | Kiểm | Kỳ vọng |
|---|---|---|
| 1 | `task check` | xanh |
| 2 | `X-Admin-Key` cũ | 401 — không còn đường vào |
| 3 | Không token / khách thường | 401 / 403 |
| 4 | `admintool grant-role` → super admin | mọi `/admin/*` được |
| 5 | Vai trò "Biên tập sản phẩm" (`catalog.products.write`) | tạo sản phẩm 201; tạo danh mục 403 |
| 6 | Thêm quyền cho vai trò đang giữ | có hiệu lực ở request KẾ TIẾP (không chờ 5 phút) |
| 7 | Gỡ vai trò khỏi người dùng | 403 ngay request kế tiếp, token vẫn còn hạn |
| 8 | Sửa/xóa `super_admin`; tự đổi vai trò mình; quyền lạ trong vai trò | 422 / 422 / 422 |
| 9 | Xóa vai trò còn người giữ | 409 `ROLE_IN_USE` |
| 10 | `/me` | có `permissions`; super admin có đủ mọi quyền trong code |
