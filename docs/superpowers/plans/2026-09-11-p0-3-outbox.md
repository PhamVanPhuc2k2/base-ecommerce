```sql
-- +goose Up
CREATE TABLE outbox (
    id             UUID        PRIMARY KEY,
    aggregate_type TEXT        NOT NULL,
    aggregate_id   UUID        NOT NULL,
    event_type     TEXT        NOT NULL,
    payload        JSONB       NOT NULL,
    trace_id       TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at   TIMESTAMPTZ,
    attempts       INT         NOT NULL DEFAULT 0,
    last_error     TEXT,
    CONSTRAINT outbox_aggregate_type_not_blank CHECK (btrim(aggregate_type) <> ''),
    CONSTRAINT outbox_event_type_not_blank     CHECK (btrim(event_type) <> '')
);

-- Index PARTIAL: bảng tích lũy hàng triệu dòng nhưng phần chưa gửi luôn nhỏ.
-- Index đầy đủ trên cột này sẽ to bằng cả bảng mà 99,99% nội dung không bao giờ
-- được đọc tới.
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;

-- Cho job dọn: tìm dòng đã gửi quá hạn.
CREATE INDEX outbox_published_at_idx ON outbox (published_at) WHERE published_at IS NOT NULL;

CREATE TABLE processed_events (
    consumer     TEXT        NOT NULL,
    event_id     UUID        NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- consumer PHẢI là một phần của khóa chính. Thiếu nó thì consumer thứ hai
    -- thêm vào ở P7 sẽ thấy mọi event đều "đã xử lý" và không làm gì cả.
    PRIMARY KEY (consumer, event_id)
);

CREATE INDEX processed_events_processed_at_idx ON processed_events (processed_at);

-- +goose Down
DROP TABLE processed_events;
DROP TABLE outbox;
```

- [ ] **Bước 4: Query**

`apps/api/internal/outbox/queries/outbox.sql`:

```sql
-- name: AppendOutbox :exec
INSERT INTO outbox (id, aggregate_type, aggregate_id, event_type, payload, trace_id)
VALUES ($1, $2, $3, $4, $5, $6);

-- name: FetchUnpublished :many
SELECT id, aggregate_type, aggregate_id, event_type, payload, trace_id, attempts
FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT $1
FOR UPDATE SKIP LOCKED;

-- name: MarkPublished :exec
UPDATE outbox SET published_at = now() WHERE id = ANY($1::uuid[]);

-- name: MarkFailed :exec
UPDATE outbox
SET attempts = attempts + 1, last_error = $2
WHERE id = $1;

-- name: DeletePublishedBefore :execrows
DELETE FROM outbox
WHERE id IN (
    SELECT id FROM outbox
    WHERE published_at IS NOT NULL AND published_at < $1
    LIMIT $2
);

-- name: DeleteProcessedBefore :execrows
DELETE FROM processed_events
WHERE ctid IN (
    SELECT ctid FROM processed_events
    WHERE processed_at < $1
    LIMIT $2
);

-- name: MarkProcessed :execrows
INSERT INTO processed_events (consumer, event_id)
VALUES ($1, $2)
ON CONFLICT (consumer, event_id) DO NOTHING;
```

⚠️ `FOR UPDATE SKIP LOCKED` là chi tiết cốt lõi: nó cho phép relay khóa đúng
những dòng nó đang xử lý mà không chặn ai khác. Nhưng nó cũng chính là lý do
**chỉ được chạy MỘT bản relay** — nhiều bản sẽ publish sai thứ tự. Xem đặc tả §8.

## Task 2: Mở rộng `domain.Event`

**Files:** sửa `apps/api/internal/catalog/domain/events.go`, `product.go`

- [ ] **Bước 1: Thêm hai method vào interface**

```go
// Event là sự kiện nghiệp vụ do entity phát ra.
type Event interface {
	EventID() uuid.UUID
	EventType() string
	AggregateID() uuid.UUID
	AggregateType() string
	OccurredAt() time.Time

	// Payload là dữ liệu đi kèm event, sẽ được marshal thành JSONB trong outbox.
	//
	// Giữ MỎNG: chỉ định danh và vài trường ổn định nhất. Consumer cần gì hơn
	// thì tự đọc lại từ database. Payload dày nghĩa là mỗi lần đổi hình dạng
	// sản phẩm là đổi hợp đồng của mọi consumer, và những event cũ nằm trong
	// outbox mang hình dạng cũ mãi mãi.
	Payload() any
}
```

⚠️ **`baseEvent` KHÔNG được cài `AggregateType()` và `Payload()`.** Để nó cài
mặc định thì thêm một event mới mà quên khai báo sẽ lọt qua trình biên dịch và
ra production với payload rỗng. Bắt buộc từng event tự khai thì quên là **không
biên dịch được** — đó là điểm của thiết kế này.

## Task 3: `internal/outbox`

**Files:** tạo `apps/api/internal/outbox/outbox.go`, `repo.go`

- [ ] **Bước 1: Record — struct hạ tầng thuần**

```go
// Package outbox cài đặt transactional outbox dùng chung cho mọi module.
//
// ⚠️ Package này KHÔNG được import bất kỳ module nghiệp vụ nào (catalog,
// orders...). Nó là hạ tầng: module dùng nó, nó không biết module nào tồn tại.
// Một lần "tiện tay" import catalog/domain để lấy một hằng số là đủ để biến
// modular monolith thành big ball of mud. scripts/check-arch.sh luật 4 chặn việc này.
package outbox

type Record struct {
	ID            uuid.UUID
	AggregateType string
	AggregateID   uuid.UUID
	EventType     string
	Payload       []byte
	TraceID       string
	Attempts      int
}
```

- [ ] **Bước 2: Repository nhận `postgres.Manager`**

```go
type Repository struct{ db *postgres.Manager }

func NewRepository(db *postgres.Manager) *Repository { return &Repository{db: db} }

// Append ghi event vào outbox. PHẢI được gọi trong cùng transaction với dữ liệu
// nghiệp vụ — đó là toàn bộ lý do outbox tồn tại. db.DB(ctx) tự lấy pgx.Tx từ
// context nếu đang trong transaction, nên gọi đúng chỗ là đủ.
func (r *Repository) Append(ctx context.Context, recs ...Record) error {
	q := gen.New(r.db.DB(ctx))
	for _, rec := range recs {
		if err := q.AppendOutbox(ctx, gen.AppendOutboxParams{...}); err != nil {
			return fmt.Errorf("ghi outbox: %w", err)
		}
	}
	return nil
}
```

Các method còn lại: `FetchUnpublished(ctx, limit)`, `MarkPublished(ctx, ids)`,
`MarkFailed(ctx, id, errMsg)`, `DeletePublishedBefore(ctx, cutoff, batch)`,
`DeleteProcessedBefore`, `MarkProcessed(ctx, consumer, eventID) (bool, error)`.

⚠️ `MarkProcessed` trả về `bool` = "dòng mới được thêm". `false` nghĩa là event
đã xử lý rồi. Đừng trả `error` cho trường hợp đó — trùng lặp là chuyện **bình
thường** trong at-least-once, không phải lỗi.

⚠️ `last_error` phải bị **cắt ngắn** (ví dụ 500 ký tự) trước khi ghi. Lỗi từ
driver có thể dài hàng KB, và một message lỗi lặp lại 10 lần sẽ làm phình bảng.

**Kiểm chứng:** viết `cmd/scratch/main.go` tạm:

1. `Append` **ngoài** transaction → dòng vẫn được ghi (dùng pool)
2. `Append` **trong** `tx.Run` rồi trả lỗi → **không** có dòng nào (rollback)
3. `FetchUnpublished` trong hai transaction song song → transaction thứ hai
   **không** thấy dòng transaction thứ nhất đang khóa (chứng minh `SKIP LOCKED`)
4. `MarkProcessed` gọi hai lần cùng `(consumer, event_id)` → lần đầu `true`,
   lần sau `false`
5. `pool.Stat().AcquiredConns() == 0` sau khi xong

Xóa `cmd/scratch` khi xong.

## Task 4: `catalog/adapter/outboxpub`

**Files:** tạo `apps/api/internal/catalog/adapter/outboxpub/publisher.go`,

- [ ] **Bước 1: Adapter dịch domain.Event → outbox.Record**

```go
// Package outboxpub cài đặt port app.EventPublisher bằng bảng outbox.
//
// Đây là chỗ kiến trúc hexagonal trả công: thay logpublisher bằng package này
// mà KHÔNG sửa một dòng nào trong domain hay app.
//
// Nó cũng là ranh giới dịch thuật: catalog/domain.Event (kiểu nghiệp vụ) trở
// thành outbox.Record (kiểu hạ tầng). Nhờ vậy internal/outbox không cần biết
// catalog tồn tại.
package outboxpub

func (p *Publisher) Publish(ctx context.Context, events ...domain.Event) error {
	if len(events) == 0 {
		return nil
	}
	recs := make([]outbox.Record, 0, len(events))
	for _, e := range events {
		payload, err := json.Marshal(e.Payload())
		if err != nil {
			// Không nuốt: payload không marshal được nghĩa là event sẽ đi ra
			// với nội dung rỗng, và consumer không có cách nào biết.
			return fmt.Errorf("marshal payload của %s: %w", e.EventType(), err)
		}
		recs = append(recs, outbox.Record{
			ID:            e.EventID(),
			AggregateType: e.AggregateType(),
			AggregateID:   e.AggregateID(),
			EventType:     e.EventType(),
			Payload:       payload,
			TraceID:       middleware.GetReqID(ctx),
		})
	}
	return p.repo.Append(ctx, recs...)
}
```

```go
// Declare tạo exchange, queue và binding. Idempotent — gọi lại nhiều lần không sao.
//
// Khai báo trong code chứ không bằng tay trên management UI: hạ tầng dựng lại
// từ đầu phải chạy được ngay, và không ai phải nhớ đã bấm những gì.
func Declare(ch *amqp.Channel) error {
	if err := ch.ExchangeDeclare("ecommerce.events", "topic", true, false, false, false, nil); err != nil {
		return err
	}
	// Queue retry: KHÔNG có consumer. Message nằm đó cho tới khi TTL hết, rồi
	// RabbitMQ tự đẩy về queue chính qua dead-letter-routing-key.
	if _, err := ch.QueueDeclare("catalog.indexer.retry", true, false, false, false, amqp.Table{
		"x-message-ttl":             int32(30000),
		"x-dead-letter-exchange":    "",
		"x-dead-letter-routing-key": "catalog.indexer",
	}); err != nil {
		return err
	}
	...
}
```

⚠️ **`x-message-ttl` hết hạn theo thứ tự ĐẦU HÀNG.** Message ở giữa hàng có TTL
ngắn hơn vẫn phải chờ message đầu hàng. Với TTL cố định 30 s cho mọi message thì
không sao. Đừng đặt TTL riêng từng message trên cùng queue này — xem đặc tả §5.1.

⚠️ Đổi tham số của một queue đã tồn tại sẽ làm `QueueDeclare` **lỗi 406
PRECONDITION_FAILED**, không phải tự cập nhật. Lúc phát triển thì xóa queue trên
management UI rồi chạy lại; lúc production thì phải tạo queue tên mới và chuyển dần.

- [ ] **Bước 4: Publisher có confirm**

```go
// NewPublisher bật chế độ confirm. KHÔNG có confirm thì ch.Publish trả về
// thành công ngay cả khi broker chưa hề nhận message — và toàn bộ ý nghĩa của
// outbox biến mất, vì relay sẽ đánh dấu published_at cho message không tồn tại.
func NewPublisher(ch *amqp.Channel) (*Publisher, error) {
	if err := ch.Confirm(false); err != nil {
		return nil, fmt.Errorf("bật confirm: %w", err)
	}
	...
}

// Publish gửi một message và CHỜ confirm từ broker.
func (p *Publisher) Publish(ctx context.Context, routingKey string, body []byte) error {
	conf, err := p.ch.PublishWithDeferredConfirmWithContext(ctx, "ecommerce.events", routingKey,
		true,  // mandatory: không route được thì trả về thay vì im lặng vứt đi
		false,
		amqp.Publishing{
			ContentType:  "application/json",
			DeliveryMode: amqp.Persistent, // không có dòng này thì broker restart là mất message
			Body:         body,
		})
	if err != nil {
		return err
	}
	ok, err := conf.WaitContext(ctx)
	if err != nil {
		return err
	}
	if !ok {
		return errors.New("broker nack message")
	}
	return nil
}
```

⚠️ `DeliveryMode: amqp.Persistent` là bắt buộc. Thiếu nó thì message nằm trong
RAM và biến mất khi broker restart — outbox bảo đảm tới được broker, không bảo
đảm broker giữ được.

⚠️ `mandatory: true` cần một goroutine đọc `ch.NotifyReturn(...)`, nếu không
message không route được sẽ bị vứt im lặng. Ghi log mức ERROR khi nhận return.

**Kiểm chứng:** viết `cmd/scratch` publish một message, xem management UI
(`localhost:15672`, app/app) thấy message trong `catalog.indexer`.

Kiểm ca thất bại: publish với routing key không khớp binding nào (`rac.rac`) →
phải thấy log ERROR từ `NotifyReturn`, **không** im lặng.

## Task 6: `cmd/outboxrelay`

**Files:** tạo `apps/api/cmd/outboxrelay/main.go`

- [ ] **Bước 1: Vòng lặp**

```
mỗi 500ms:
  tx.Run:
    recs = FetchUnpublished(100)        // FOR UPDATE SKIP LOCKED
    nếu rỗng → return nil
    với mỗi rec:
      dựng envelope → publish (chờ confirm)
      lỗi → MarkFailed(rec.ID, err), ghi log WARN, BỎ QUA rec này
    MarkPublished(các ID thành công)
```

⚠️ `MarkPublished` chỉ nhận **những ID publish thành công**. Đánh dấu cả lô khi
chỉ một phần thành công sẽ làm mất event vĩnh viễn — và không có lỗi nào ở đâu.

⚠️ Publish nằm **trong** transaction là cố ý: nếu tiến trình chết sau khi publish
mà trước khi commit, transaction rollback và event được publish **lại** ở vòng
sau. At-least-once, đúng như thiết kế. Consumer khử trùng lặp.

## Task 7: Consumer và `cmd/worker`

**Files:** tạo `apps/api/internal/platform/rabbitmq/consumer.go`,
`apps/api/cmd/worker/main.go`

- [ ] **Bước 1: Consumer**

`qos.Prefetch = 10`, manual ack. Với mỗi message:

```
parse envelope
  lỗi parse → nack(requeue=false) → thẳng DLQ. ĐỪNG retry: message hỏng cú pháp
              thử lại 5 lần vẫn hỏng, và trong lúc đó chiếm chỗ của message tốt
đếm x-death → nếu >= 5 → publish sang DLQ, ack, log ERROR
xử lý trong transaction:
  MarkProcessed(consumer, event_id) → false nghĩa là đã xử lý → ack, bỏ qua
  ... xử lý nghiệp vụ ...
lỗi tạm thời → publish sang catalog.indexer.retry, ack bản gốc
thành công → ack
```

⚠️ `MarkProcessed` phải nằm **trong cùng transaction** với xử lý nghiệp vụ. Tách
ra thì có khe cửa: đánh dấu xong, crash trước khi xử lý → event mất vĩnh viễn mà
bảng nói là đã xử lý.

⚠️ Prefetch không giới hạn (mặc định) nghĩa là broker đẩy toàn bộ queue vào RAM
của worker. Với queue tồn đọng lớn thì worker chết vì OOM ngay khi khởi động.

- [ ] **Bước 2: `cmd/worker` — chỉ ghi log**

Worker P0.3 chỉ ghi `event_id`, `event_type`, `trace_id`, `payload`. Giá trị của
nó là chứng minh đường đi hoạt động; P7 thay phần xử lý bằng indexer Meilisearch.

**Kiểm chứng — sáu mục, không bỏ mục nào:**

| # | Kiểm | Kỳ vọng |
|---|---|---|
| 1 | Tạo sản phẩm | Log worker có `event_id` **và** `trace_id` khớp request HTTP |
| 2 | **Publish lại cùng `event_id`** | Worker bỏ qua, `processed_events` **không** thêm dòng |
| 3 | Message JSON hỏng | Vào **thẳng** DLQ, không quay vòng |
| 4 | Lỗi tạm thời (tắt Postgres) | Vào retry queue, 30 s sau quay lại |
| 5 | Quá 5 lần | Vào DLQ, log ERROR, message **vẫn còn** trong DLQ |
| 6 | Giết worker giữa lúc xử lý | Message **không** mất: chưa ack thì broker giao lại |

Mục 2 dựng lại bằng cách publish tay qua management UI với đúng `event_id` cũ.
